# 活动实现难度排序

> 分析日期：2026-08-29　|　分析对象：`data/excel/activity_table.json`（basicInfo 全量活动）、`app/game/modules/`（活动及大玩法模块）、`design-spec.md` / `docs/module-audit-2026-08-29.md` / `docs/接口覆盖分析-未实现与stub清单.md`（现状证据）、PRTS 活动一览与各玩法条目（机制参照）
> 目的：为活动开发排定优先级，从"低成本高复用"到"攻坚型大玩法"给出可执行的难度分级。

---

## 一、排序依据

难度评估综合三方面证据：

1. **机制复杂度**（prts.wiki）：该玩法在官服是什么形态——纯领奖、标准关卡、独立小游戏、战斗规则扩展，还是存档/联机型大玩法。
2. **基建复用度**（本项目代码）：能否直接复用既有 battle / templateShop / mission / medal / checkin / inventory-pipeline 管道；复用越多难度越低。
3. **现状与验证成本**（审计/抓包）：当前是真实实现、简化实现还是 stub；是否有官服抓包样本可校准数值（无样本的模块实现后仍要补抓包验证）。

难度分五档（1 最易 → 5 最难）。

## 三、各档排序理由

### 第 1 档：纯领奖类（难度 1/5）

prts.wiki 上属于"登录活动 / 纪念活动"类，机制只有"点一下领奖"，服务端不需要任何新状态机。checkin 模块的通用领取管道（getCheckInReward / getActivityCheckInReward / getChainLogInReward 等）可直接覆盖 60 个 CHECKIN_ONLY 及 LOGIN_ONLY / PRAY_ONLY / BLESS_ONLY / SWITCH_ONLY 等同类。

**已实现（2026-08-29）**：CHECKIN_ONLY（`getActivityCheckInReward`，含动态签到日 `dynOpt` → `dynItemDict`）、LOGIN_ONLY（`loginOnly/getReward`）、SWITCH_ONLY（`getSwitchOnlyReward`）、CHECKIN_VS（`actCheckinvs/sign`，按已签天数取 `checkInDict`）、CHECKIN_ALL_PLAYER（`checkinAllPlayer/getActivityCheckInReward`）均从 excel 读奖励、经 `player.gainItem` 管道发放、防重复领取；COLLECTION 此前已实现（milestone）。PRAY_ONLY / BLESS_ONLY / CHECKIN_ACCESS / CHECKIN_VIDEO / UNIQUE_ONLY 本地 excel 无奖励配置（仅 basicInfo/homeActConfig/dynActs），按"不猜值"约束保留 stub + TODO 注明数据源与官服抓包样本。RECRUIT_ONLY 为公招标签活动（机制在 gacha，无领奖接口），MISSION_ONLY / AVG_ONLY 无领奖接口，均不在第一档领奖接口范畴。

### 第 2 档：标准支线 / 故事集 / 主线（难度 2/5）

占 excel 里的大头（60 个 TYPE_ACT9D0 + 18 个 MINISTORY + 3 个 TYPE_MAINSS）。核心价值都在关卡与剧情，服务端只需把"关卡解锁 → 掉落 → 商店兑换 → 任务领奖 → 勋章"接到既有基建上，基本零新机制。复刻活动（`isReplicate=true`）可直接复用原版播种逻辑。这一档的主要工作是一次性把播种/商店/任务做成通用化，之后批量覆盖。

### 第 3 档：带专属小玩法的支线（难度 3/5）

这是**工作量分水岭**：每项多一个独立的客户端小游戏，服务端要按抓包补齐该游戏的专属路由语义（act35side 商店买卖、act38side 拼图状态、act42side 经营天数推进、act46side 挖矿等）。act44side 情报屋已验证这条路可行——靠 21KB 的 informant.ts 完整实现营业日状态机，是本档的参考样板。

### 第 4 档：战斗规则扩展（难度 4/5）

机制是"战斗结算 + 活动专属规则"，复杂度中等但**往往缺抓包样本**。审计报告明确列出 bossRush finish、enemyDuel、vecBreakV2、interlock 均无实包验证，实现后还要靠抓包校准数值，风险主要在验证而非编码。bossRush（尖灭测试）已完整实现，可作为本档的参照系。

### 第 5 档：独立大玩法（难度 5/5）

本档包含两类高难度玩法：

- **存档/经营型**：生息演算（sandbox V2/V3）需要存档读档、区块图、敌袭迁移、建造/烹饪/科技树的多层状态，是当前路由面最大且几乎全空的模块（V2/V3 约 50 条 202 stub），也是审计报告点名的 P0。
- **联机型**：卫戍协议（autochess）与促融共竞（multiplayer）本质是多人玩法，单机私服只能做"假多人"占位，协议面大且语义复杂。

rlv2 与 arkhub 虽然同属本档难度，但项目内已有完整实现（前者 64 端点 + 约 355 个用例，后者含独立 TCP 网关与 ARKDEX 状态层），可作"已攻克"的参照系。

## 四、建议实现顺序

按"性价比 + 风险低"推进：

1. **第 1 档收尾**：纯领奖 stub 转真实发放，接入 inventory-pipeline。
2. **第 2 档批量复用**：60 个支线走标准管道，把播种/商店/任务一次做通用化。
3. **第 3 档逐个攻克**：优先已有抓包的 act27side，参考 act44side 情报屋样板。
4. **第 4 档补战斗规则**：优先抓包证据充分的项目，边实现边校准。
5. **第 5 档攻坚**：sandbox 生息演算（抓包最密却最空），随后是 autochess / multiplayer。
