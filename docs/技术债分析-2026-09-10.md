## 1. 【根因级】质量门禁三道闸门全部失效

这是**唯一一条会自我放大其他所有债务的债**。下面三个问题各自独立，合起来意味着：从 2026 年某时起，`any` 的增长、未使用导入的堆积、覆盖度下滑，**都不会有任何自动反馈**。

### 1.1 ESLint 完全跑不起来 🔴

```
$ pnpm exec eslint app
Error: typescript-eslint does not support TS 7.0.        (exit 2)
```

- 版本对峙：`typescript@7.0.2`（原生编译器）vs `typescript-eslint@8.67.0`（peer 要求 `typescript <6.1.0`，官方 issue #10940 仍在追）。
- 项目已在 `.npmrc` 用 `legacy-peer-deps=true` **强行绕过 peer 检查**（`.npmrc` 注释自述），使安装可完成——但**换来的是 eslint 运行时直接抛错**。
- `eslint.config.mjs:9` 引用了 `tseslint.configs.recommended`，其中包含 `no-explicit-any`——**该规则从未执行过一次**。这与 1432 处 `any` 是因果关系，不是巧合。
- 叠加：`package.json` 的 26 个 scripts 中**没有 lint 条目**，`AGENTS.md` 也明确写「No lint script exists」。**配置写了，但从未接入流程，且接入会立刻崩。**

**修复**：二选一——(a) 侧装 TS 6 API 供 eslint 使用（TS 7 官方支持 side-by-side）；(b) 降 `typescript` 到 6.x 直到 typescript-eslint 支持 7。随后 `"lint": "eslint app"` 接入验证顺序。**先以 warn 落地 `no-unused-vars` / `no-explicit-any`，因为它能立刻消掉 3400+ 行无效代码（见 §3.2）。**

### 1.2 覆盖率工具链崩溃，阈值形同虚设 🔴

`pnpm run test:coverage` 连续 3 次以 unhandled error 结束，`coverage-final.json` / `index.html` **均未生成**：

```
Unhandled Error: ENOTEMPTY: directory not empty, rmdir '...\coverage\.tmp'
Unhandled Error: ENOENT: open '...\coverage\.tmp\coverage-0.json'
   at V8CoverageProvider.readCoverageFiles (@vitest/coverage-v8/dist/provider.js:32)
```

- 我做过两次消解实验：把 `--coverage.reporter=text` 单独使用 → 不再报 ENOENT；把 `--coverage.reportsDirectory` 指向仓库外 → 报「Something removed the coverage directory」。**结论：崩溃来自 `vitest.config.mts:16-28` 的 `reporter: ['text','html','json','lcov']` 与报告目录的交互，而非测试本身。**
- 后果：`vitest.config.mts:21-27` 的 `thresholds`（lines 40 / functions 35 / branches 25 / statements 40）**永远不会被评估**。
- 更值得警惕的是**阈值本身就设得太松**：配置注释自述实测 ~51% 行 / 47% 函数 / 41% 分支，即阈值比现值低 10~16 个百分点——**即使工具修好，也能容忍覆盖度腰斩式回退**。

## 2. 正确性 / 安全债：已实测到的真实缺陷

### 2.1 🔴 P0 — `/activity/autochessSeason/*` 18 条真实路由被 stub 遮蔽，整个模块 HTTP 面成为死代码

- **遮蔽链**：`app/game/routes.ts:95` 挂载 `/activity → ./modules/activities`，而 `activities/index.ts:53` 先 `router.use(typeActRouter)`；`typeAct/router.ts:236-261` 用循环注册了 **18 条** `/autochessSeason/*`，全部 `validateBody(activityStubSchema)` 且 handler 只 `res.send(player.delta)`。
- `app/game/routes.ts:137` 才挂载 `/activity → ./modules/autochess/routes`（18 条**真实实现**，含校验与 `player.autoChess.*` 业务调用，:73/81/92/…）。
- Express `app.use` **按注册顺序匹配**，且 `app/game/app.ts:128` 明确注释「顺序即挂载顺序」，`:135-146` 串行 `app.use`。**先注册者胜 → 客户端全部自走棋请求落到空 stub。**
- **测试为何没发现**：`tests/` 中 `autochessSeason` 仅 3 处命中，**全是 manager 级单测**（`autochess-manager.test.ts:65/130/295`），没有任何 HTTP 层用例——典型「单测全绿、HTTP 面已死」。
- **修复**：删除 `typeAct/router.ts:236-261`；更根本的是**补一条「同一 (method,path) 不得被多模块重复注册」的路由唯一性守卫**——目前 7 个架构守卫里没有这一条，而 §2.4 显示这类冲突至少还有 2 处。

### 2.2 🔴 P0 — `POST /shop/buyLMTGSGood` 缺负数量守卫（货币复制）

- `shop/logic/misc.ts:21-25` 的 `_assertBuyCount` 文档**亲口写明**「负数 count 使价格/发放数量取反…反向入账（免费刷信用/凭证/钻石等货币）」。
- 6 个 `buy*` 中 5 个已加该守卫（`fes.ts:47/88/128`、`low-high.ts:63/105/185`），**唯独 `fes.ts:207 buyLMTGSGood` 漏了**，只剩 `:221 _assertAffordable` 与 `:223 _assertAvail`。
- 两道现有防线都拦不住负数：`_assertAffordable` 在 `count <= 0` 时**直接 return**（`misc.ts:64`）；`_assertAvail` 只查上界（`misc.ts:97-99`）。
- 入口 schema 也不校验正数：`shop/schemas.ts:69-72` 为 `count: z.number()`（全仓 9 处 count 字段同款）。
- 路由**在线**：`shop/handler.ts:715`；`:235-237` 会以 `good.price.count * count` 负值走 `items:use`。
- **修复**：`fes.ts:221` 前补 `mgr._assertBuyCount(count);`，并加负数量单测；更彻底的是把 `count: z.number()` 改为 `z.number().int().positive()`（9 处一次改完，从入口堵死）。

### 2.3 🔴 P0 — `AdminService.listUsers` 的「容错分支」必抛 TypeError，把局部失败放大为全量失败

- `app/ops/admin/AdminService.ts:417`：`return toUserSummary(uid, undefined as any);`
- 而 `toUserSummary`（`:250-251`）第一行就是 `const status = pd._playerdata.status;` → **undefined 解引用必抛 TypeError**。
- 该语句位于 `catch` 块内（`:416`），异常穿透 catch、拒绝该 `async` 回调的 promise → `:411` 的 `Promise.all` **整体 reject** → `listUsers` 全量失败。
- 即：**某个 uid 存档加载失败（本应只影响该行）会让整个管理端用户列表 500**。`as any` 恰好把这层真实类型错误静音了。
- **修复**：`toUserSummary(uid, pd: PlayerDataManager | undefined)` 返回可空摘要；或删掉这个 catch 让它 fail-fast 并带 uid 上下文。

## 3. 类型强制力债

### 3.1 严格度开关：`tsc` 通过 ≠ 安全 🔴

已开：`strict: true`（含 `noImplicitAny` / `strictNullChecks`）。**未开**的开关及其**实测破坏面**（用继承根配置、只加单个 flag 的变体 tsconfig 实跑）：

| 未开的开关 | app 内实测报错数 | 风险 |
|---|---|---|
| `noUncheckedIndexedAccess` | **1741**（122 文件） | 所有 `arr[i]` / `map[key]` 被当作必然存在；用户/Excel 数据缺失时 undefined 一路蔓延进存档，而不是早期抛错。热点 `medal.ts` 768、`mission/templates/stage.ts` 162 |
| `noUnusedLocals` | **4098** | 死代码无反馈（与 §3.2 的 3400+ 未用导入同源） |
| `noUnusedParameters` | 341 | — |
| `noPropertyAccessFromIndexSignature` | 334 | `admin-router.ts` 90、`freshPlayer.ts` 84 |
| `noImplicitReturns` | 91 | `core/auth/auth.ts:93,131,307` 等漏 return |
| `exactOptionalPropertyTypes` | 48 | 可选属性 undefined 语义宽松 |
| `noImplicitOverride` | **9** | 一天可清完 |

**建议**：不要一次全开。先开 `noImplicitOverride`(9) 和 `noImplicitReturns`(91)；`noUncheckedIndexedAccess` 先在 `app/core/**` 与 `app/game/kernel/**`（错误最少）打开并写进 AGENTS.md 的验证顺序；`medal.ts` 必须先做 §4.1 的重构。

### 3.2 `any` 逃逸：1432 处，且有明确的结构性成因

- 类型位置共 **1432 处**（754 `:any` + 678 `as any`；另有 87 处 `.any` 成员访问已排除）；**141 / 402 个 app 文件含 any，43 个文件 ≥10 处**。
- 模块分布：`roguelike` **355**、`medal` **179**、`building` **160**、`ops/admin` **100**、`activities/arkhub` 58、`shop` 52。
- **成因不是随手写的**，而是两个可复制的模式：
  1. **`medal.ts` 的 161 个 `{ [key: string]: (args: any) => void }` 分发表**——占该文件 92% 的 any。180 个勋章模板方法全靠字符串名动态调用（`:417/:433` `(this as any)[template](...)`），编译期零校验；配合 `:240` 的类级索引签名。传错 mode 会在运行时 `undefined is not a function`。
  2. **活动容器未类型化**——`(draft.activity as any)` 类 68 处 / 20 文件、`activity as any` 57 处 / 18 文件。每个活动都得靠断言描述自己写进 `activity`/`tshop` 的形状，字段改名不报错、跨活动污染无法发现。
- 另有两类可批量消除的：`excel.X as any` **65 处 / 30 文件**（生成类型字段缺失所致）、`as unknown as` **65 处**（`capture-manager.ts` 三处把 `db.all()` 的 `unknown[]` 直接断言成实体数组）。
- `@ts-ignore/@ts-nocheck` **全仓 0 处**；`@ts-expect-error` 仅 3 处且全在 `kernel/events/runtime.ts:109/128/275`（事件总线签名收窄）。**这 3 处压在「所有 manager 的事件订阅」这一根节点上**——Emittery 升级或 EventMap 改名不会报错，建议补一个编译期一致性断言。

### 3.3 非空断言 401 处，其中两组由**外部输入**驱动 🟠

- 热点：`excel/excel.ts` **60**（全部是 `BattleEquipTable!: ...` 型 definite-assignment，声明「加载完成前访问即爆炸」，数据表缺失时无法给出可诊断错误）。
- **`activities/act42side/router.ts`：15 处**，形态为 `act[body.activityId!].taskMap[body.taskId!]`（`:142,143,164-166,178-180`）——**把请求体字段断言为非空后直接当索引**。
- `character/char.ts`：14 处，`:139` `excel.charData(charId)!.potentialItemId!` 是**双重断言**，charId 不在表中即 TypeError。
- **修复**：char.ts 统一改 `const info = excel.charData(id); if (!info) throw ...`；excel.ts 的 60 个字段改 `T | undefined` + `requireX()` 取值器。
