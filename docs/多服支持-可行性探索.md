# 多服支持可行性探索（B服 / 日服 / 韩服 / 美服 / 台服）

> 探索日期：2026-08-17 · 目标：评估在当前私服（国服官方）基础上，扩展支持 Bilibili 服、日服（YoStarJP）、韩服（YoStarKR）、美服/国际服（YoStarEN）、台服（txwy）的可行性，并给出改造方案。
> 口径说明：`实测` = 本次已直接请求验证；`待确认` = 需后续客户端逆向/抓包验证。

---

## 1. 结论速览

1. **代码骨架与"哪个服"基本解耦**。游戏协议路由（routers/managers/battle/mission/medal…）、excel 加载器、抓包转发（capture 模式 as/gs 主机已可配置）、统一日志/抓包存储都是"服务器无关"的。真正的分服工作集中在 **9 个改造点**（见 §6），大部分是"把写死的国服常量变成 region 维度配置"。
2. **支持难度排序（低→高）**：
   - **B服** ★：数据与国服同源同版本，**数据管线零改动**，只需接 bilibili 账号 SDK 登录。
   - **台服** ★★：conf 与 CDN **已实测可用且结构与国服完全一致**（可复用现有下载/解包/转换管线），需独立数据目录 + 本地账号收敛 + 版本服务。
   - **美服/日服/韩服** ★★★：YoStar 三服 conf 路径、FBS schema、AES 密钥均**未实测通**，需要先逆向 YoStar 客户端；社区已有解码后的 excel 数据仓库可作过渡数据源。
3. **推荐落地顺序：B服 → 台服 → YoStar 三服**；架构上先把 `region` 提升为一等配置维度（§6 方案），后续每服只是"加一条配置 + 一个 auth provider"。
4. 多服代理属于灰色地带且涉及第三方 SDK（bilibili / Yostar / txwy），建议仅作技术探索与个人学习用途（§8）。

### 3.1 本次实测的关键事实

1. **台服数据管线可直接复用**：
   - `https://ak-conf-tw.gryphline.com/config/prod/official/Android/version` → `{resVersion, clientVersion}`，格式与国服相同；
   - `https://ak-tw.hg-cdn.com/assetbundle/official/Android/assets/{resVersion}/hot_update_list.json` → 返回 `{versionId, abInfos[]}`，与国服热更清单结构**逐字段一致**（13822 个 bundle，含 `anon/` 前缀 excel bundle）。
   - 结论：`official-excel.ts` 只需把 `HU`/`CONF_VERSION` 参数化即可拉台服数据；AES 密钥（MASK_V2）是否一致待用台服 bundle 实测（大概率一致，同 Unity 代码基）。
2. **YoStar 三服 conf 域名存在但 `/config/prod/official/Android/version` 404**（nginx/cloudflare 均响应）。可能是路径结构不同、渠道名不同，或需特定 UA/参数——**必须靠抓包/反编译 YoStar 客户端确认**，无法靠猜。
3. **YoStar 三服 excel 数据已有社区解码产物**：`Kengxxiao/ArknightsGameData_YoStar`（ja_JP / en_US / ko_KR），表名与国服白名单一致（activity_table / character_table / stage_table / item_table…），可作过渡数据源或对照；但仓库更新频率与时效性不可控。
4. **Yostar 账号体系**：社区确认 2025 年起实装 Yostar ID（JP `account.yostar.co.jp`、EN `account.yo-star.com`、KR `account.yostar.kr`），支持邮箱+密码与"联动 ID / 联动码"——登录链路与国服手机号体系完全不同。项目 `misc-alignment.ts` 已为 `/account/yostar_auth_request|submit`、`/user/yostar_createlogin`、`/yostar/get-auth` 打了 stub，可作为真实实现的起点。
5. **B服渠道路径 404**：`/config/prod/bilibili/Android/version` 在国服 conf 上 404，说明 B 服客户端很可能走的就是国服 `official` 路径（渠道差异只在账号 SDK），但需 B 服客户端实测确认。B 服数据内容与国服同版本，**数据侧零成本**。
6. 探测环境有系统级代理/DNS 改写（部分 *.hypergryph.com 域名被解析到 127.0.0.1），域名 IP 不可作为证据，以上结论均基于真实 HTTP 响应。

## 4. 分层差异分析（共享 vs 差异）

### 4.1 可复用（不动或微调）
- 游戏协议与全部业务路由/管理器（战斗、任务、勋章、基建、抽卡逻辑、arkhub…）——各服协议同构。
- excel 数据结构整体同构（表名一致，仅数值/文案不同）。
- capture 抓包转发、统一抓包存储、统一日志、管理后台、SSE。
- host-router 骨架（改为"按子域名前缀分发 + 区域域后缀表"即可）。

### 4.2 必须分服的差异面
| # | 差异面 | 说明 |
|---|---|---|
| D1 | **数据管线参数** | conf URL / CDN 基址 / resVersion / 平台路径（Android vs Windows）；**FBS schema 每服每版本一套**（CN 的 fbs-schemas 不能直接用于 YoStar）；MASK_V2 密钥需逐服实测；本地化表（init_text / main_text / charword / handbook…）数值不同 |
| D2 | **版本服务** | `majorVersion` / `clientVersion` / `resVersion` 逐服，客户端强校验，错一个就登录失败 |
| D3 | **conf / network_config** | 每服端点模板不同（gs/as/u8/hu/hv/sl…），appConfig（支付/客服/协议）逐服 |
| D4 | **账号系统（最大工作量）** | 国服手机号密码；B服 bilibili SDK（passport + 授权码）；YoStar 三服（邮箱密码 + 联动码）；台服 txwy SDK |
| D5 | **域名分发** | 需识别 `.arknights.jp` / `.arknights.global` / `.arknights.kr` / `gryphline.com` / `yo-star.com` 等域后缀，并按 Host 选择 region |
| D6 | **单账号/多账号语义** | 跨服共存时 uid 命名空间与 secret 收敛需按 region 隔离（或坚持单实例单 region） |
| D7 | **卡池详情** | `gacha_detail_table.json` 逐服卡池不同，`gacha-sync` 需按 region 落盘 |
| D8 | **数据目录** | `data/excel/`、`data/user/` 需按 region 分目录或运行时切换（excel.ts 路径表硬编码） |
| D9 | **公告/商店** | announce_meta、商店 goodList 逐服 |

## 5. 方案设计

### 方案 A：单实例多服（推荐终态）
`data/config.json` 增加 `regions` 表，每服一条：
```jsonc
{
  "region": "cn",                       // 当前默认 region（或按 Host 自动识别）
  "regions": {
    "cn":  { "dataDir": "./data/excel",        "confApi": "https://ak-conf.hypergryph.com", "cdn": "https://ak.hycdn.cn",            "as": "https://as.hypergryph.com",       "gs": "https://ak-gs-gf.hypergryph.com", "auth": "phone",      "version": { "major": "446", "client": "2.7.61", "res": "26-08-07-14-53-29_30b8f0" } },
    "tw":  { "dataDir": "./data/excel-tw",     "confApi": "https://ak-conf-tw.gryphline.com", "cdn": "https://ak-tw.hg-cdn.com",     "as": "待逆向",                             "gs": "待逆向",                             "auth": "txwy",       "version": { "major": "?", "client": "35.7.01", "res": "26-07-24-10-43-30_d453ab" } },
    "jp":  { "dataDir": "./data/excel-jp",     "confApi": "https://ak-conf.arknights.jp",      "cdn": "https://ark-jp-static-online.yo-star.com", "as": "待逆向",                       "gs": "待逆向",                             "auth": "yostar",     "version": "待逆向" },
    ...
  }
}
```
- host-router 按 Host 域后缀选 region，`excel.ts` / conf 服务 / 版本服务 / auth 全部读当前 region 配置。
- 多服 excel 同时进内存：约 60 张表 × 每服，内存与类型对齐（types 为 CN 生成，跨服同名字段结构若漂移需运行时容错）是主要代价。

### 方案 B：每服独立实例（推荐先做验证）
同一份代码，每服一份 `config.json` + 数据目录，进程级隔离。改动最小（只需"参数化"不需要"多路共存"），先验证每服协议/数据是否跑通，再演进到方案 A。

> 建议：**先 B 后 A**。B 阶段的参数化改造（§6 的 1/2/3/5/7）在 A 阶段全部复用，不浪费。

## 7. 分阶段路线图

### Phase 0 · 前置确认（纯调研，关键路径上的"未知项"必须先落地）
1. **抓包/反编译 B 服客户端**（com.hypergryph.arknights.bilibili）：确认 conf 路径、登录接口（bilibili SDK 授权码 → token 交换）。
2. **抓包/反编译台服客户端**（tw.txwy.and.arknights）：确认 gs/as 域名、登录协议、announce 路径。
3. **抓包/反编译 YoStar 客户端**（JP 优先）：确认 conf/network_config 真实路径、gs/as 域名、MASK 密钥、FBS schema 差异、Yostar 登录链路（挑战码格式）。
4. 用官方 CDN 实测拉取各服 excel 并跑通现有解密（台服已验证结构一致，落地密钥验证；YoStar 用社区仓库对照）。
5. 确认各服 `majorVersion` 与客户端校验逻辑。

### Phase 1 · 试点两服（先 B 服、后台服）
- **B服**：只做 auth provider（bilibili），数据零成本；验证"同一国服数据 + 不同登录"的完整链路。
- **台服**：改造 #1/#2/#4/#6/#7 落地，`--region tw` 拉数据、按域响应版本/conf；auth 先用本地账号收敛（跳过 txwy SDK）打通游戏内。

### Phase 2 · YoStar 三服
- 基于 Phase 0 逆向结论补齐参数与 schema；实现 yostar auth（联动码）；对协议差异（新玩法 rlv2/arkhub 等若客户端版本新于国服）逐接口复测路由覆盖度（现有 `scripts/_diff-client-routes.py` 可复用到各服客户端）。

### Phase 3 · 多服共存
- 方案 A 落地（单实例多 region）、管理后台多服切换、公告/商店逐服、`pnpm run update --region` 全服批量更新。

## 8. 风险与未知项

1. **合规风险（最重）**：多服私服涉及 bilibili / Yostar / txwy 第三方 SDK 与海外运营商，风险显著高于国服单机私服；建议仅技术探索/个人学习，不对外分发。
2. **YoStar conf 路径未知**：404 的原因（路径结构/渠道名/UA 限制）只能靠客户端逆向确认，是本探索最大不确定项。
3. **FBS schema 漂移**：每服每版本一套 schema，CN 的 `scripts/vendor/fbs-schemas` 不可直接复用；schema 生成依赖各服反编译（`scripts/schema-gen.ts` 需按服跑）。
4. **AES 密钥（MASK_V2）**：CN 密钥对台服大概率适用，对 YoStar 未知；若不同需逆向提取。
5. **版本碎片化**：CN 2.7.61 与台服 35.7.01 为两套版本体系，客户端协议字段可能有分支差异（国服近期玩法 arkhub/rlv2 在旧版客户端可能不存在），路由覆盖需逐服重测。
6. **账号 SDK 闭源**：bilibili/Yostar/txwy 登录流程均为黑盒，需抓包逆向；联动码机制（Yostar）可能是绕过注册的最短路径。
7. **社区数据仓库时效性**：`ArknightsGameData_YoStar` 为第三方维护，更新节奏不可控，仅作过渡。
8. **多服并存成本**：方案 A 下多份 excel 常驻内存、types 跨服兼容（字段增减用 `any` 兜底或按服类型）。

## 9. 结论

- **可做，且国服代码基已为它做了大半铺垫**（capture 主机可配、yostar 端点已 stub、bilibili 渠道已有 stub、管线结构清晰）。
- **建议顺序：B服（零数据成本）→ 台服（管线已实测可复用）→ YoStar 三服（需先逆向）**。
- **第一步动作**（Phase 0）：抓包 B 服与台服客户端确认账号链路与 gs/as 域名，同时拉台服 excel 跑通解密验证密钥——这两件事做完，Phase 1 就有了全部输入。
