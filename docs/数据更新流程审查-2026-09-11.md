## 1. 【P0】类型生成被静默跳过，但上报成功

`scripts/update-data.ts:145-157`：

```ts
function generateTypes(): boolean {
  log(`生成 TypeScript 类型...`);
  // 类型生成已切换到 CS 反编译源（reference/com.hypergryph.arknights_2.7.61.cs），
  const csFile = path.join(__dirname, "../reference/com.hypergryph.arknights_2.7.61.cs");
  if (!fs.existsSync(csFile)) {
    // 新 clone 场景：reference/ 被 gitignore，类型文件已跟踪——跳过再生成而非失败
    log(`跳过类型生成：缺少 ${csFile}（类型文件已随仓库跟踪；放回反编译源后可重新生成）`);
    return true;          // ← 返回 true = 成功
  }
  return executeCommand("pnpm exec tsx scripts/generate-types.ts", path.join(__dirname, ".."));
}
```

**实测**：

```
$ ls reference/com.hypergryph.arknights_*.cs
reference/com.hypergryph.arknights_2.7.71.cs      # 只有 2.7.71，没有 2.7.61
```

于是每次 `pnpm run update` 走的都是 `return true` 分支：`main()` 里 `if (!generateTypes())` 判定为通过，最终打印 `===== 数据更新完成 =====` 且 `return 0`。

**为什么这条最致命**：它把「新表结构导致类型滞后」这个**本应显式暴露的信号**变成了静默通过。excel 表结构一旦新增字段，`types_excel_gen.ts` 不更新 → 业务代码读不到新字段但不报错（因为是可选成员或索引访问）→ 只能靠人工发现。而 `main()` 的 return code 是 CI / 启动脚本判断成败的依据，现在它恒为 0。

**注**：注释里的「新 clone 场景 reference/ 被 gitignore」这个理由**本身成立**（`AGENTS.md` 也确认 `reference/` gitignored），问题在于它用「按名字存在性判断」而不是「按通配探测」，导致「文件在、只是改名了」被误判成「文件不在」。

**修复**（与 `cs2schema.ts` 已有的正确实现对齐）：

```ts
function resolveCsFile(): string | null {
  const dir = path.join(__dirname, "../reference");
  if (!fs.existsSync(dir)) return null;
  const cands = fs.readdirSync(dir)
    .filter((f) => /^com\.hypergryph\.arknights_.+\.cs$/.test(f))
    .sort();
  return cands.length ? path.join(dir, cands[cands.length - 1]) : null;
}
```

并把「跳过」的返回值改为 `true` 仅当**确有已跟踪的类型文件**；否则应返回 `false` 让 `main()` 返回非 0。至少要把 `log` 改成 `logWarn`，并让 `main()` 的尾行结论里带上「类型未再生」标记。

## 3. 【P1】增量判断仅比 mtime → 已产生 28 张陈旧表，且校验假通过

`scripts/excel-convert.ts:150-163`：

```ts
export function isUpToDate(rawFile: string, outFile: string, schemaFile?: string): boolean {
  const decStat = fs.statSync(rawFile);
  const outStat = fs.existsSync(outFile) ? fs.statSync(outFile) : null;
  const schemaStat = ...;
  return !!outStat
    && decStat.mtimeMs <= outStat.mtimeMs
    && (!schemaStat || schemaStat.mtimeMs <= outStat.mtimeMs);
}
```

判据只有「raw 不新于 out **且** schema 不新于 out」。**实测磁盘状态**：

```
$ ls data/excel/*.json | wc -l        → 63
$ # raw 更新于 final 的表数
raw 更新于 final 的表数: 28 | final 较新: 35 | 无 raw: 0
```

具体样本：

| 表 | raw 解码时间 | final 输出时间 | 差 |
|---|---|---|---|
| `gamedata_const` | 2026-09-10 19:07 | 2026-09-09 12:19 | 30h |
| `uniequip_table` | 2026-09-10 19:05 | 2026-09-09 12:19 | 30h |
| `building_data` | 2026-09-10 19:05 | 2026-09-09 12:19 | 30h |
| `gacha_table` | 2026-09-10 19:07 | 2026-09-09 12:19 | 30h |
| `character_table` | 2026-09-10 20:35 | 2026-09-10 20:39 | ✅ 一致 |

28 张陈旧表全量清单：`arkvent / battle_equip / building_data / building_local_data / campaign / chapter / char_master / char_meta / charm / checkin / climb_tower / clue_data / cooperate_battle / crisis / crisis_v2 / display_meta / enemy_database / enemy_handbook / ep_breakbuff / extra_battlelog / favor / gacha / gamedata_const / handbook / handbook_team / hotupdate_meta / sandbox_perm / uniequip`。

**根因**：转换阶段的 `needConvert = targets.filter(... !isUpToDate(...))`（`official-excel.ts:324-331`）**本身逻辑是对的**——raw 比 out 新就该重转。所以问题不在过滤条件，而在于：**上一轮（9-10 20:2x）的转换阶段只跑了 35 张表就结束了**（`data/excel` 的 35 张是 Sep 10、28 张是 Sep 9），而这 28 张的 raw 是 9-10 19:0x 解码的——即**解码完成在 19:0x，转换阶段却把这 28 张判成了「已最新」**。

由于这些 raw 是 Sep 10 19:05，而 9-9 12:19 的 final 更早，「raw 应更新于 final」→ `isUpToDate` 应返回 `false` → 应被重转。它们没被重转只有两种可能：

1. 那一轮 `--table` 定向转换只覆盖了 35 张（`--table` 模式下 `targets` 被缩小），而后续没有跑过一次全量；
2. 转换阶段的 worker 分支（`needConvert.length >= 4 && !tableArg`）里 worker 抛错被吞（见 §5），导致 fail 未累计、被当作 skipped。

**无论哪种，结论一致**：**当前 `data/excel` 是一个混合新鲜度的数据集（35 新 + 28 旧）**。而 §4 的版本校验恰好因为「两批数据的 `dataVersion` 都是 76.2.0」而通过——校验器只看这一个字段，看不到混合状态。

**另外**：`data/excel/data_version.txt` **没有任何脚本写入方**（`grep -rn "data_version" scripts/ app/` 只命中读者与注释，无 `writeFile`）。它是一个**手工维护 / 直接入库的产物**（mtime Sep 9 12:19，与 28 张旧表同批次）。这意味着 S10 校验的「基准值」本身不受管线控制。

**修复建议**：
- `isUpToDate` 增加**内容级判据**：在 out 里埋一个 `_meta: { sourceMtime, schemaHash, sourceResVersion }` 字段（或旁挂 `.meta.json`），比对 sourceMtime/schemaHash 而非文件系统 mtime。mtime 会被 checkout / 复制 / 备份还原污染，**天然不可靠**。
- 转换阶段结束时显式打印 `skipped` 明细（当前只打印计数），并让 `--table` 定向模式下把未覆盖的表标记为「未刷新」，避免混合数据集被当成完整数据集。
- `data_version.txt` 应由解码阶段从 hotupdate 描述符**自动落盘**，不应手工维护。

## 4. 【P1】S10 版本校验因陈旧数据恰好同版本而假通过

`app/game/excel/data-version.ts` 的校验逻辑是 `data_version.txt#VersionControl` vs `gamedata_const#dataVersion`。实测：

```
data_version.txt VersionControl = 76.2.0
gamedata_const.dataVersion      = 76.2.0
一致? YES -> verifyLocalDataVersion 通过
```

问题在于：这 28 张陈旧表里包含 `gamedata_const` 自身（Sep 9），而 `data_version.txt` 也是 Sep 9 —— **两者「同批次地旧」**，所以比对一致。校验器无法区分「都是最新」和「都是旧的」。

**更有意思的佐证**：`gamedata_const` 的 raw（Sep 10 19:07）**不含 `dataVersion` 键**，而 final（Sep 9）**含**。说明 `dataVersion` 不是从官方 raw 里来的，而是转换阶段注入/上游补的。也就是说这个「版本指纹」的来源链本身不清晰——`verifyLoadedDataVersion` 拿它当权威，但它并不直接映射到官服热更版本（官服指纹是 `resVersion` = `26-09-03-04-06-11_79371a`）。**建议把 S10 的判据换成 `resVersion`**，那才是官服真正的时间戳。

**修复建议**：S10 增加第二判据——比对 `data/excel/*.json` 的文件集合 mtime 是否**同批**（例如 max(mtime) - min(mtime) 超阈值即报警），或直接以 `resVersion` 为准。当前实现只能发现「转换中断在版本切换处」，发现不了「部分表没重转」。

## 5. 【P2】转换 worker 的错误被吞，fail 计数不准

`scripts/convert-worker.ts`（40 行）：正常路径 post `{name, status:"ok"|"fail"|"skipped"}`，最后 post `{done:true}`。但 `worker.on("error")` 与写文件失败的 `else` 分支只 `resolve()`，**不 `fail++`、不 post fail 消息**。后果：

- `official-excel.ts:353` 的 `else if (m.status === "fail") { fail++ }` 收不到这些失败；
- 最终 `转换完成: N ok, M fail` 的 M 被低估；
- 顶层 `if (fail > 0) return false?`（需确认）如果不触发，`pnpm run update` 认为管线成功。

结合 §3 的「28 张没被重转」，**这条高度可能是那一轮的漏网原因**——若这些表在 worker 里抛错，错误被吞、fail 不增、脚本报成功，而 `data/excel` 保持旧文件。**这条优先级应视为 P1，因为它能解释 §3 的成因。** 建议：worker 的错误分支必须 `post({name, status:"fail", error})` 且主线程统计后非零即让管线返回失败。

## 6. 【P2】热更清单快照与 `resVersion` 硬编码陈旧

## 7. 【P2】`cs2schema.ts` 未接线，schema 漂移无自动守卫

`scripts/cs2schema.ts`（309 行）是整个参考数据链路里**质量最高**的一个脚本，自带两道安全阀：

1. 解析阶段 `fieldCtx.size > 0`（遇到无法解析的字段）→ 保留旧字段表；
2. 新表字段数少于旧表 → 保留旧字段表（注释记录 `skin_table` 曾一次丢 30953 spots）。

且它支持 `--check`（与现有 schema 逐字段比对，回归验证）、`--write`、`--table`、`--diff`。**但它没有出现在 `package.json` 的任何 script 里**（`grep -rn "cs2schema" package.json` 零命中），也没有 CI（`docs/技术债分析-2026-09-10.md` §0 已确认仓库无 CI）。

结果：**FBO schema 与 C# 客户端之间的漂移没有任何自动化发现机制**。2.7.71 那次 `Torappu.ItemData` 新增 `reslockStatus`/`canReslock` 造成的 slot 错位（症状：天文数字的向量长度 → V8 `Invalid string length` → OOM）是**人工跑 `cs2schema` 发现的**，下一次不会这么幸运。

**修复**：加 `"schema:check": "tsx scripts/cs2schema.ts --check"` 并在反编译流程（`pnpm run decompile`）末尾自动调用；有 CI 后作为必过门禁。

## 9. 做得对的地方（不要动）

站在「两条链路」的视角，以下实现质量明显高于同类项目，重构时务必保留：

1. **`TABLE_WHITELIST`（63 条）与解码集、转换集三方严格一致**——实测 63/63 表可解析、0 损坏，没有多解一张、也没有漏解一张。
2. **枚举转换的双层设计**：FBS 权威 + CS 仅补充已有值 + `fbsNames` 过滤，彻底解决了历史上「数值字段被 CS 枚举字符串污染」的问题。实测 `playerApMap = [82,84,86,88,90,...]`、`characterExpMap[0][3] = 151`、`evolveGoldCost = [[-1,-1],...]` 全部为数值，零污染。
3. **畸形 camelCase 防御**：`BROKEN_KEY_RE = /^[a-z][A-Z]/` 拒绝对 `rELIC`/`dEFAULT`/`cOLLECTION` 的学习 + `RENAME_ALLOWLIST = ["lmtgsid"]` 白名单。实测全库仅剩白名单内的 `gacha_table.*.lMTGSID`。
4. **`AsNumpy` 影子键清理**：raw 里 7 个 `*AsNumpy`，final 里残留 0。
5. **dict 容器递归修复**：`isDictContainer` 下钻，解决了 2026-08-14 那次「dict 容器被 null 记录字段污染」的崩溃。
6. **有界并发**：下载池 cap 6 / 解码池 cap CPU / 转换 ≥4 张走 `worker_threads`，参数可覆盖（`EXCEL_DECODE_CONCURRENCY`）。
7. **`update-data-sync.test.ts` 三绿**（89ms）：`syncGameVersion` 的 Android+Windows 双版本、无变化容忍、HTTP 500 → false，都覆盖到了。
8. **`cs2schema.ts` 的两道安全阀**（§7），是整个链路最应该被推广到其他环节的设计模式。
9. **`data-version.ts` 刻意不 import `excel` 单例**，避免循环依赖——细节到位。
