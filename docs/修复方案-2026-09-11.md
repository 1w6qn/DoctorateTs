## 0. 三条原则

1. **先固化，再收敛。** 任何「约定」先落成会红的守卫测试，再谈批量修改。
   未覆盖的约定必然失效（§1-F1 就是活样本）。
2. **迁移必须语义等价。** `emit("items:get", [X])` ≡ `add(X).handle()`，
   迁移批次里**不夹带**任何行为变更。行为修复单独成阶段。
3. **每阶段独立可交付、可回滚。** 阶段之间不共享未合并的改动。

### F2 细节（迁移前置，必须先修）

`PlayerDataManager.gainItem` 是懒建后**长期复用**的实例：

```ts
get gainItem(): GainItemPipeline {
  if (!this._gainItemPipeline) this._gainItemPipeline = new GainItemPipeline(this, this._trigger);
  return this._gainItemPipeline;
}
```

而 `PlayerDataManager` 实例经 `accountManager.getPlayerData(uid)` 缓存、跨请求存活。
于是：调用方 `add(...)` 之后若在 `handle()` 之前抛错，`_targets` 会**留到下一个请求**，
被下一次 `handle()` 一并发放 —— 迁移面扩大 84 处后，这个隐患被同步放大。

### F3 细节（最小改动、最高收益）

```ts
rewardMedal(args: { medalId: string; group: string }) {   // ← 不是 async
  ...
  this._trigger.emit("items:get", [items]);               // ← 未 await，async 事件的 fire-and-forget
  return items;
}
```

三个调用方**都已写好 `await`**，所以加 `async` + `await emit` 是纯收益修复：
代码表面语义不变，实际行为从「竞态」变为「串行」。这是全清单里性价比最高的一处。

### 1.1 修 F3：medal 奖励发放

**注意**：`onMedalComplete`(:143) 内的自动发奖路径同样受益，确认其也在 await。

### 1.2 修 F2：pipeline 队列回收

**推荐方案（A）**：在 `delta` getter 收尾 + 错误处理器双点回收。

```ts
// inventory-pipeline.ts：clear() 已存在，直接复用为终态回收
// PlayerDataManager.ts delta getter 末尾
const out = { ...base };
this._gainItemPipeline?.clear();   // 请求边界回收，防止队列跨请求残留
return out;
```

```ts
// app/game/app.ts gameErrorHandler：异常路径同样回收（否则抛错请求会漏）
try { ... } finally { getPlayerOptional()?.gainItem?.clear(); }
```

选择 `delta` 作为回收点的理由：`res.send(player.delta)` 是每个请求的必经出口，
是天然的请求边界，不需要引入新概念（httpContext 作用域）。

**备选方案（B，更彻底）**：把 pipeline 做成请求级实例（经 `httpContext` 建/取）。
彻底但改动面大，且需要处理 `player.gainItem` 的所有取值点。**建议留待阶段 5 评估。**

**验证**：新增单测 ——
① `add()` 后不调 `handle()`，再取一次 `delta`，断言队列已空；
② recipe 内抛错后，断言队列为空。

## 4. 阶段 3 —— 收敛（分批迁移 84 处）

**统一迁移映射**（语义等价，逐条机械替换）：

```ts
// 发放
await player._trigger.emit("items:get", [[item]]);
→ await player.gainItem.add(item).handle();

// 发放（批量数组）
await player._trigger.emit("items:get", [items]);
→ for (const i of items) player.gainItem.add(i); await player.gainItem.handle();
//   等价写法：await player.gainItem.add(...items).handle()  ← 注意 add 是单参，不可用

// 消耗
await player._trigger.emit("items:use", [[cost]]);
→ await player.gainItem.add(cost).use();
```

> ⚠️ `add(bundle)` 是**单参**签名（`inventory-pipeline.ts:63`），批量必须循环。
> 若希望支持 `add(...bundles)`，属 API 变更，建议单独评估而非混在迁移里。

### 批次表（按风险递增，每批独立提交）

| **B** | 活动族：act24side / charm / shared / interlockRefresh / milestone / openServer / arkhub | 18 | 低-中 | 多为纯发放 |

**批次 D 特别说明**：`battle.ts` 的 emit **发生在 `update()` recipe 内部**
（`battle.ts:1123` 注释：「奖励发放经 `_trigger.emit("items:get")` 在配方内同步入账」）。
